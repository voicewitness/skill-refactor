# 002 升级：旧版 skr 改出来的产品，在新版下怎么识别、怎么适配

skill-refactor 是底层工具。它产出的东西（`skr cli init` 生成的 CLI 目录，下面叫「产品」）会在它之外继续活着、被用户改；
而 skill-refactor 自己的判据（[001 方法](001-method.md)）和协议库也会继续迭代。所以必须回答：一个按旧判据生成、又被人改过的产品，在新版下哪里不合格、谁来改、怎么改才不毁掉用户的改动。

## 三条规矩

1. **产品带身份证。** 每个产品目录里有 `skr.lock.json`：哪版 skr（`skr`）、哪版判据（`method`）、哪版协议库（`runtime`，三个库文件内容的指纹）、
   以及生成时每个文件的指纹（`files`）。工具每次替它改了文件，也记一笔（`applied`）。
2. **识别靠检查，不靠比版本号。** 版本号只说明「是哪版生成的」，说明不了「现在满不满足」—— 用户可能早就自己改好了，也可能改坏了。
   所以每条升级规则直接去看产品本身：清单、处理器、库文件。没有身份证的产品（身份证出现之前生成的，或被删了）照样查得出来。
3. **用户改过的不覆盖。** 一个文件现在的指纹和身份证里记的一样，说明是生成时的样子，工具可以直接改（`auto`）；
   不一样，或者没有记录可比，就当用户改过，只给一张卡片说清怎么改（`manual`）。要写业务代码的（例如 `next` 怎么推出卡片）永远是 `manual`。

## 怎么用

```
skr upgrade check <产品目录> --json     # 每条没过的规则一张卡片：upgrade_auto（工具能改）/ upgrade_manual（说清怎么改）
skr upgrade apply <产品目录> --json     # 修掉 auto 的；--only <id,…> 只修这几条
```

全部规则都过了，身份证上的 `method` 才升到现在这一版；还有没过的就保持原样，下次 `check` 照样列出来。
改造对象登记过产品目录的，`skr next` 会在身份证的判据版本落后时出 `upgrade_due` 卡片。

## 规则长什么样

规则在 `core/upgrades.mjs` 的 `RULES` 里，每条：

| 字段 | 含义 |
|---|---|
| `id` | 规则名，`--only` 用它 |
| `since` | 从哪版判据起要求的 |
| `rule` | 对应 001 方法里的哪条（P3、H1 …） |
| `detect(产品)` | 看产品本身，不合格返回一句说明，合格返回 null |
| `fix(产品)` | `auto` 或 `manual`（同一条规则，看文件有没有被改过决定） |
| `how` | manual 时怎么改 |
| `apply(产品)` | auto 时工具怎么改，返回改了哪些文件（会重新记指纹） |

现在有：身份证缺失（lock）、协议库过期（runtime）、argv 缺 `--json`（argv-json）、清单不自洽（catalog）、闸门命令没拦自签（gate-self）、`next` 还是空壳（next）。

## 升判据的人要做什么

改了 001 方法里的条目，就要升 `core/plan.mjs` 的 `METHOD`，并且：

1. 在 `core/upgrades.mjs` 的 `METHOD_HISTORY` 末尾加上新版本；
2. 至少写一条 `since` 是新版本的规则：旧产品在新判据下哪里会不合格、能不能自动改、不能的话怎么改。

测试会查这两件事：判据升了却没写升级规则，测试不过。这样「判据变了，旧产品怎么办」不会被忘掉。

## 不在这里的

- **不是 skr 生成的 CLI**（例如在 skill-refactor 之前手写的工具）：没有 `commands.mjs`，`upgrade check` 会拒收。它们要先走一遍改造（`skr target add` …），或者以后按 `<工具> protocol --json` 读清单来查清单级的规则（还没做）。
- **数据迁移**：判据变化如果要求改存储（例如某样状态从文件挪进 SQLite），迁移脚本在产品自己的 CLI 里写，升级规则只负责把这件事查出来、写清楚。
