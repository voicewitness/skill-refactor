# 000 理念：skill-refactor 要解决什么，怎么走，舍掉了什么

## 目标

一个 skill 通常是一份写给 agent 的长手册，加几个脚本。它能跑起来，靠的是 agent 每次都把手册读对、把每一步都记得、把用户的每句回答都存下。
跑久了，这三件事总有一件会漏：

- 做到哪了说不清：会话一断、换一个 agent，就从头猜。
- 人的回答只在聊天里：照着做了却没记，下一轮又问一遍；或者转述时走了样。
- 手册里写着「必须 / 不要」：执行者照样漏，漏了也没人发现。

skill-refactor 的目标是把这样的 skill **改造成工具能接住的样子**：做到哪了由工具从记录里算出来，人的点头和规则由工具执行，agent 只做判断。
具体是三样产物：类工具调用的命令清单（协议层）、每样状态只有一个正本的存储方案、`next` 推出卡片的可 pull 流程。判据见 [001 方法](001-method.md)。

**怎么算做成了**：改造之后，随便哪个 agent、在会话断掉之后，只调一次 `next` 就知道接下来做什么；用户回答过的事不会被再问一遍；手册里能变成检查的规则，违反了会被拒收，而不是靠人发现。

## 理念

1. **状态在记录里，不在模型的上下文里。** 上下文会断、会被压缩、会换人。所以「做到哪了」必须能从磁盘上的记录重新算出来，而不是让 agent 记住。
2. **代码定，模型判。** 能确定的交给代码：谁写了哪个文件、哪一行在不在、哪些步骤还没登记、方案依据有没有过期。要理解才能下的判断交给模型：这一步到底是什么、这份数据是正本还是派生、哪条规则能变成检查。工具层不调用模型。
3. **人的权威不能代理。** 批准、拍板、确认必须是用户本人说的、原话照抄。执行者签不了，这条由工具强制，不写在提示里指望它自觉。
4. **不发明新协议，借最通用的形状。** 各家 agent 框架描述工具的方式几乎一样：名字、说明、JSON Schema 参数。命令清单就照这个写，所以能直接导出给任何一家；命令本身仍是命令行，任何能跑 shell 的 agent 都能用。
5. **能变成检查的规则，就不留在提示里。** 提示里的规则靠记忆，检查靠代码。变不成检查的，才留给 agent 按需取用。
6. **一份计算。** 看板上「还剩什么」和 agent 拉到的卡片，必须是同一个函数算的。两边各算各的，迟早会出现看板说没做完、agent 手里却没有对应待办的情况（在 acceptkit 上真实发生过）。
7. **工具自己先照着走。** skill-refactor 改造别人时用的是同一套：它有自己的命令清单、`next`、卡片、要用户批的闸门、执行记录。它要是自己都走不顺，产出的方案也不可信。
8. **判据会错，所以要能被纠正。** 每次执行都记一条，用户说「不对」时记下原话和哪条判据错了；判据有版本，改了要升版本。

## 路径：为什么是这几步、这个顺序

```
盘点（工具读事实）→ 登记流程和存储（agent 判断，带依据）→ 出方案（工具按登记确定性生成）
  → 用户批 → 生成 CLI 骨架 → 填处理器 → 检查
```

- **先盘点，再判断。** 让 agent 直接读手册写方案，每次写得都不一样，也说不清依据。先由工具把事实摆出来（流程候选、命令、谁写了什么、要人点头的句子、只写在提示里的规则），agent 在这个基础上判断，漏看的地方会少很多。
- **判断要逐条登记，每条带「文件:行」。** 这样方案里每条建议都能追回原文；工具核对行号，编出来的依据过不了。登记是这次改造里唯一要花脑子的部分，也是最值得留下来的部分。
- **方案由登记确定性生成。** 同样的登记出同样的方案；登记一改，方案的依据就变，`next` 会提示重出，批过的也要重新批。方案不是 agent 的一篇作文，而是登记的投影，所以可以比较、可以复现。
- **用户批了才生成。** 方案决定了以后的命令和存储，是要用户负责的决定，所以放在闸门后面。
- **只生成骨架，不生成实现。** 命令清单、参数检查、`--json` 卡片、各家格式导出、闸门的自签检查、表结构，这些能从方案确定地推出来，就生成；每条命令具体怎么读写业务数据，从手册推不确定，留给处理器去写。
- **最后检查。** 清单自不自洽、导出后满不满足各家的规则、拷入的协议库是不是最新的。

## 取舍

| 选了 | 没选 | 代价 | 换来 |
|---|---|---|---|
| 工具层不调用模型 | 让工具自己读手册、写方案 | 盘点是启发式的，有噪音也会漏，要 agent 逐条补 | 可复现、零依赖、换哪家 agent 都一样；判断留在宿主模型里，不用再配一套模型 |
| 登记要依据（文件:行） | 自由登记 | 登记慢 | 每条判断能被核对，编不出来 |
| 方案是模板化的投影 | 让 agent 设计完整 schema | 表结构粗（id + data JSON + rev），不是最终设计 | 定下来的是「正本在哪、谁写、要不要事务」这几件最容易错的事；具体列在写处理器时细化 |
| 生成骨架，处理器手写 | 生成完整实现 | 处理器还要写，尤其是 `next` 怎么从记录推出卡片 | 不假装能从手册推出业务逻辑 |
| 命令行是主通道 | 只做 MCP server | 每次调用起一个进程 | 任何能跑 shell 的 agent 都能用；要 MCP 时导出清单、用 `argvFor()` 把调用转回命令行，拒收和记录照旧 |
| 状态正本放 SQLite | 文件 / JSON | 人不能直接手改状态 | 事务、并发安全、不丢更新；人要直接读写的资产（用例、知识、手册）仍是文件 |
| 改造记录放 `~/.skill-refactor` | 写进被改造的 skill 目录 | 改造记录和 skill 分开放 | 不污染被改造的 skill；产物（方案、清单、表结构）可以拷走 |
| 格式库靠人核对、带出处 | 自动抓各家文档 | 会过时 | 不会被一个错误页面悄悄带偏；每条都有核对日期，过时一眼可见 |
| 插件共用一个本机服务、一个端口 | 每个改造各起一个服务 | 插件在同一进程里，一个插件出错要靠服务兜住 | 一个地址看全部；插件只写页面，不用管端口、进程、鉴权 |

## 不做的事

- **不改被改造的 skill 的手册和数据。** skill-refactor 只出方案和骨架；改手册、迁数据由用户批了以后在新 CLI 里做。
- **不替用户批任何东西。**
- **不评判 skill 要不要存在。** 只管把已经决定要做的流程变得接得住。
- **不做通用的 agent 框架。** 没有自己的循环，循环写在手册里，由宿主 agent 跑。

## 已知的不足

- 生成的 `next` 是空的。从记录推出卡片是改造后最难的一块，现在完全留给处理器。可以先按「这一步写的实体里有没有这条主体的记录」生成一个默认实现。
- 只有方案、没有迁移工具：方案里写了迁移步骤，但一次性导入的脚本要自己写。
- 盘点只认得 JS、Python、Shell 里常见的写盘写法，以及手册里「写到 / 追加」这类说法；别的写法会漏，要靠登记补。
- 「做成了」的标准还没有自动度量，现在要拿改造前后的真实记录对比（例如 acceptkit 改造前漏存的拍板数）。
